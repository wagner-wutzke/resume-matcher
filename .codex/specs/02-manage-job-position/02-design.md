# Technical Design: Job-Offer Management

- **Status:** [ ] Draft | [x] Approved for Implementation
- **Author/Agent:** @architect
- **Reference Spec:** `01-requirements.md`

## 1. Architecture

Extend the existing Spring Boot SPA with job-offer management using the existing `job_offers`
MongoDB collection. Spring MVC serves the static frontend from
`src/main/resources/static` and handles `/api/job-offers`; Spring Data MongoDB provides
persistence.

Keep components in the existing `net.wowdev.ai.resume.matcher` package and follow the existing
model, repository, service, DTO, controller, and exception-handler patterns. The service validates
create and update requests and persists create, update, and delete operations. The controller maps
results and errors to HTTP responses. The browser keeps at most one selected offer in state.

Use the existing individual MongoDB connection properties. Do not configure or use
`spring.mongodb.uri`. Do not place credentials in source-controlled configuration; optional
credentials are provided by environment properties.

## 2. Data Model and Field Mapping

Use the existing `job_offers` collection and map MongoDB `_id` to API `id`.

The create/update request contains these seven editable fields:

| Request field            | Persisted field          | Meaning                           | Validation                                        |
|--------------------------|--------------------------|-----------------------------------|---------------------------------------------------|
| `company`                | `company`                | Hiring company name               | Required                                          |
| `jobName`                | `jobTitle`               | Job Name                          | Required                                          |
| `jobDescription`         | `jobDescription`         | Job description Markdown source  | Required                                          |
| `requiredQualifications` | `requiredQualifications` | Qualifications Markdown source   | Required                                          |
| `yearsOfExperience`      | `yearsOfExperience`      | Years of professional experience | Required numeric value                            |
| `location`               | `location`               | Job location                      | Required                                          |
| `allocation`             | `allocation`             | Work allocation                   | Required; one of `Remote`, `Hybrid`, or `On-site` |

Treat null, empty, and whitespace-only required strings as invalid. `jobId` is generated by the
server and is not part of the request or form. Persist the required numeric Years of Experience
value. The API response exposes the job title as `jobTitle` and includes the generated `jobId`.

Generate a unique Job ID for each new offer in the format `JD-########`, beginning with
`JD-00000001` when no generated IDs exist and incrementing the numeric suffix for each new offer.
The recruiter does not enter or edit this identifier. Persist sequence state atomically so
concurrent creates receive unique values. Return the assigned value in the saved offer for display
in the list.

## 3. REST API

All endpoints use `/api/job-offers`.

### `GET /api/job-offers`

Return the existing catalog using `200 OK`; an empty collection returns `[]`. Each catalog entry
contains `id`, `jobId`, `company`, `jobTitle`, `jobDescription`, `requiredQualifications`,
`yearsOfExperience`, `location`, and `allocation`. These names follow the existing catalog
response contract. The list uses `jobTitle`, `company`, and `jobId` in the required label format.

### `POST /api/job-offers`

Accept the seven editable request fields. Validate and persist the offer, generate its sequential
`jobId`, assign the MongoDB `id`, then return `201 Created`, the saved response, and a `Location`
header for `/api/job-offers/{id}`. The response includes `jobId` and `yearsOfExperience` so the
frontend can add, select, and display the created offer.

### `PUT /api/job-offers/{id}`

Accept the seven editable fields and update the identified offer while preserving its generated
`jobId`. Resolve the identifier before saving; do not upsert. Return `200 OK` and the saved
response, or `404 Not Found` if the identifier does not exist.

### `DELETE /api/job-offers/{id}`

Delete the identified offer and return `204 No Content`, or `404 Not Found` if it does not exist.

### Errors

- Invalid create/update data returns `400 Bad Request` with stable code
  `JOB_OFFER_VALIDATION_FAILED`, a general message, and field-addressable errors.
- Unknown identifiers return `404 Not Found` with stable code `JOB_OFFER_NOT_FOUND`.
- MongoDB read failures return `503 Service Unavailable` with code `JOB_OFFERS_UNAVAILABLE`.
- MongoDB write failures return `503 Service Unavailable` with a stable persistence error code.
- Error responses do not include credentials, stack traces, or internal exception details.

## 4. Open Positions List, Selection, and Details

- Load the catalog once from `GET /api/job-offers` on page load.
- Display each offer as a selectable, non-button list entry with the exact text format
  `[jobTitle] - [company] - [jobId]`.
- Selecting an entry clears any previous selection and displays the selected offer's details.
- Display Company above Job Description. Display the Job Name and the other existing offer details
  in the Details panel. Render Job Description and Required Qualifications as Markdown as described
  in Section 6.
- Keep **New Job Offer** visible. Show **Edit** and **Delete** only when an offer is selected.
- After a successful create, add the returned offer to the list, select it, and display its details.
  After a successful edit, update the list and details and keep that offer selected. After a
  successful delete, remove the offer and clear the Details panel.
- A failed write leaves the list and selected details unchanged and displays an error.

Offer entries are selectable non-button list entries. Implement keyboard and assistive-technology
interaction for selection without using button elements. Item 15's shared styling applies only to
actual job-offer buttons; offer list entries are excluded.

## 5. Create and Edit Form

Use one modal and form for create and edit. Create mode opens with empty Company, Job Name, Job
Description, Required Qualifications, Years of Experience, Location, and Allocation fields. Edit
mode loads the selected offer's current values into those fields. Years of Experience uses a
numeric input and is required.

Allocation is a select with exactly `Remote`, `Hybrid`, and `On-site`. Validate required fields
when Save is submitted, not before. If fields are missing, keep the modal open, highlight only
invalid fields, and associate an accessible required message with each invalid field.

Store the form's opening values to detect edits. Cancel closes an unchanged form immediately. If
values changed, show a custom discard prompt. Discard closes without saving; continuing to edit
closes the prompt and preserves the entered values.

## 6. Markdown and Safe Rendering

Store Job Description and Required Qualifications as Markdown source. Render them in the Details
panel with a client-side Markdown renderer configured to disable raw HTML, then sanitize generated
markup before insertion. Render Company, Job Name, Location, Allocation, list labels, and error text
as text.

## 7. Button Styling

Apply the **New Job Offer** button's visual style, `0.75rem` font size, and `35px` height to all
actual buttons in the job-offer feature, including action, form, close, and discard-confirmation
buttons. Selectable offer entries are non-button elements and are excluded from this button styling
requirement.

The requirements now make Years of Experience required and persisted. It remains in Details as
required by the SPA Skeleton's existing detail-view acceptance criterion. The list semantics and
generated Job ID decisions are also captured in the requirements; the design is ready for
implementation.

## 10. Boundaries

- Do not add candidate persistence, ingestion, matching, ranking, or recommendation behavior.
- Do not add form fields beyond the seven editable values described in the requirements.
- Do not add authentication or authorization behavior.
- Do not configure `spring.mongodb.uri`.
- Keep implementation behavior traceable to `01-requirements.md`.
